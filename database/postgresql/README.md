# PostgreSQL — versão espelho do banco (OBRIGATÓRIO)

> ## Regra obrigatória do projeto
>
> Toda alteração em `database/migrations/*.sql` ou `database/seeds/*.sql` (MySQL, usado em
> produção) **precisa** ser acompanhada da regeneração desta pasta **no mesmo commit**.
>
> Antes de commitar qualquer mudança de banco, rode:
>
> ```bash
> python3 tools/build_postgres_sql.py            # regenera database/postgresql/
> python3 tools/build_postgres_sql.py --validar  # instala num PostgreSQL real e confere
> python3 tools/check_sql_parity.py              # falha se esta pasta estiver atrasada
> ```
>
> O `check_sql_parity.py` compara o `sha256` do arquivo MySQL com o cabeçalho do `.pg.sql`
> correspondente. Se o MySQL mudou e o PostgreSQL não, o comando termina com erro — é o
> lembrete automático para não deixar a versão PostgreSQL para depois.

## Por que esta pasta existe

A produção roda em MySQL/MariaDB na HostGator. Para que uma migração futura de banco (para
PostgreSQL, Amazon RDS, Supabase, Neon etc.) não exija reescrever o DDL na mão, todo o schema
e os dados de apoio são mantidos também em PostgreSQL, gerados automaticamente a partir das
migrations MySQL. A estrutura fica idêntica: mesmas tabelas, colunas, índices, chaves
estrangeiras, restrições e dados iniciais.

## Arquivos

| Arquivo | Conteúdo |
|---|---|
| `0001_core_schema.pg.sql` | usuários, perfis, permissões, tenants, auditoria |
| `0002_cnpj_lookup.pg.sql` | cache e rate-limit da consulta de CNPJ |
| `0003_finance_schema.pg.sql` | contas, categorias, centros de custo, lançamentos, investimentos |
| `0004_user_registration.pg.sql` | cadastro, OAuth (Google/Microsoft), rate-limit de login, painel |
| `0005_banks.pg.sql` | catálogo de bancos brasileiros (código COMPE) — 464 instituições |
| `0001_admin_seed.pg.sql` | perfis, permissões e usuário admin inicial |
| `0002_finance_seed.pg.sql` | categorias e centros de custo padrão |
| `somase_instalacao_completa.pg.sql` | instalação completa (schema + seeds + bancos) |
| `somase_atualizar_banco.pg.sql` | atualização incremental, idempotente, sem apagar dados |

Todos os arquivos são **idempotentes**: podem ser executados mais de uma vez sem duplicar
dados nem dar erro.

## Como usar

Instalação em banco novo:

```bash
createdb somase
psql -d somase -f database/postgresql/somase_instalacao_completa.pg.sql
```

Atualização de banco existente (só aplica o que falta):

```bash
psql -d somase -f database/postgresql/somase_atualizar_banco.pg.sql
```

Teste rápido com Docker, sem instalar nada:

```bash
docker run --rm -e POSTGRES_PASSWORD=somase -p 5432:5432 -d --name somase-pg postgres:16
docker exec -i somase-pg psql -U postgres -c "CREATE DATABASE somase"
docker exec -i somase-pg psql -U postgres -d somase < database/postgresql/somase_instalacao_completa.pg.sql
docker exec -i somase-pg psql -U postgres -d somase -c "SELECT COUNT(*) FROM banks"   -- 464
```

Ordem de carga usada nos arquivos consolidados: **schema base (0001–0003) → seeds →
migrations restantes (0004+)**. Essa ordem é necessária porque a 0004 concede a permissão
`access_admin_panel` ao perfil `admin`, que só existe depois dos seeds.

## Regras de conversão aplicadas

| MySQL | PostgreSQL | Observação |
|---|---|---|
| `INT UNSIGNED AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` | `UNSIGNED` não existe; aceita `id` explícito em cargas |
| `TINYINT(1)` | `smallint` | flags `0/1` continuam aceitando inteiros (compatível com o PHP atual) |
| `ENUM('a','b')` | `varchar(n)` + `CHECK (col IN (...))` | mesma garantia de domínio, sem tipo nativo |
| `JSON` | `jsonb` | indexável e consultável |
| `DATETIME` | `timestamp` | sem fuso, como no MySQL |
| `ON UPDATE CURRENT_TIMESTAMP` | gatilho `somase_set_updated_at()` | um gatilho por tabela que tem a coluna |
| `KEY idx (...)` | `CREATE INDEX IF NOT EXISTS idx ...` | fora do `CREATE TABLE` |
| `INSERT IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` | idempotente |
| `INSERT ... ON DUPLICATE KEY UPDATE` | `INSERT ... ON CONFLICT (chave) DO UPDATE SET ... = EXCLUDED....` | usa a chave única da tabela |
| `FROM DUAL` | removido | PostgreSQL não usa |
| `ENGINE=InnoDB`, `CHARSET`, `COLLATE`, `COMMENT` de coluna | removidos | sem equivalente direto no DDL |
| `` `coluna` `` | `"coluna"` | identificadores citados, sempre em minúsculas |

## O que ainda não está convertido

Estes arquivos cobrem **o banco** (DDL + dados). O código PHP continua MySQL:

- as consultas dos Models usam PDO/MySQL (`backticks`, `FIELD()`, `ON DUPLICATE KEY`);
- funções como `FIELD()` e `DATE_FORMAT()` precisam ser reescritas para PostgreSQL;
- o driver seria `pdo_pgsql` e a classe `App\Core\Database` precisaria montar DSN `pgsql:`.

Ou seja: numa migração futura, o banco já está pronto e o trabalho restante é a camada PHP
(Models/Services), que pode inclusive rodar em paralelo mantendo o MySQL em produção.

## Passo a passo de uma migração futura

1. Criar o banco PostgreSQL e rodar `somase_instalacao_completa.pg.sql`.
2. Copiar os dados reais do MySQL (`mysqldump --compatible=postgresql` ou um script de ETL
   próprio), respeitando a ordem das chaves estrangeiras.
3. Ajustar `App\Core\Database` para `pgsql:` e revisar as queries dos Models.
4. Rodar `tests/SmokeTest.php` apontando para o PostgreSQL antes de trocar o `.env` de produção.
5. Só então virar o `DB_*` da produção.

## Atualizar o catálogo de bancos

A lista de bancos vem do cadastro de instituições do Banco Central (via BrasilAPI), guardada
em `database/data/bancos_brasil.json`:

```bash
python3 tools/build_banks_sql.py --baixar   # atualiza o snapshot e gera a migration 0005
python3 tools/build_sql.py                  # regera os pacotes MySQL
python3 tools/build_postgres_sql.py         # regera a versão PostgreSQL
```

## Nunca edite estes arquivos à mão

`database/postgresql/*.pg.sql` é saída do gerador. Qualquer ajuste manual é perdido na próxima
execução. Se a conversão estiver errada, corrija `tools/build_postgres_sql.py` (e valide com
`--validar`).
